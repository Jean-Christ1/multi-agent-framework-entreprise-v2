# ETL Schema Validation Tests

## Overview

The ETL Schema Validation test suite validates that Parquet files generated by the ETL demo match the schema definitions in `ascend_schema.yaml`. This ensures data quality and schema compliance throughout the ETL pipeline.

## Location

```
tests/integration/test_etl_fixtures.py
```

## Purpose

These tests serve as automated quality gates to verify:

1. **Schema Compliance**: All columns in generated Parquet files are defined in the source schema
2. **Type Safety**: Data types in Parquet files are compatible with schema definitions
3. **Data Integrity**: Non-nullable columns contain no null values
4. **Documentation**: Schema YAML file is valid and complete

## Test Coverage

### Input Files Validation (`TestInputParquetFiles`)

Tests validate source data files in `tests/fixtures/trafic_ascend/inputs/`:

- **test_input_files_exist**: Verifies that input Parquet files are present
- **test_input_column_names_match_schema**: Validates column names against schema
- **test_input_data_types_compatible**: Checks data type compatibility
- **test_input_non_nullable_columns_have_no_nulls**: Ensures no nulls in required columns

### Expected Output Validation (`TestExpectedParquetFiles`)

Tests validate expected output files in `tests/fixtures/trafic_ascend/expected/`:

- **test_expected_files_exist**: Verifies that expected output files are present
- **test_expected_column_names_match_schema**: Validates column names
- **test_expected_data_types_compatible**: Checks data type compatibility
- **test_expected_non_nullable_columns_have_no_nulls**: Validates required columns

### Schema Consistency (`TestSchemaConsistency`)

Tests validate the schema definition itself:

- **test_schema_file_is_valid_yaml**: Ensures schema YAML is well-formed
- **test_all_input_files_have_schema_definition**: Verifies all tables have definitions

## Schema File Structure

The schema is defined in YAML format at:

```
tests/fixtures/trafic_ascend/schemas/ascend_schema.yaml
```

### Schema Format

```yaml
version: '1.0'
generated_at: '2026-01-08T06:38:22.708409Z'
source_system: SAP_BODS
tables:
  table_name:
    category: source
    datastore: DS_TRAFIC_ASCENDFEED
    database: AscendFeed
    owner: DBO
    columns:
    - name: COLUMN_NAME
      type: VARCHAR|INT|DATETIME|etc
      size: 50
      nullable: true|false
    primary_key:
    - COLUMN_NAME
```

## Type Mapping

The validation uses PyArrow for schema inspection. Type mapping from YAML to PyArrow:

| YAML Type | PyArrow Types |
|-----------|--------------|
| VARCHAR   | string, large_string |
| CHAR      | string, large_string |
| INT       | int32, int64 |
| BIGINT    | int64 |
| DATETIME  | timestamp (all variants), string (for test fixtures) |
| DATE      | date32, date64 |
| DECIMAL   | decimal128, float64 |
| FLOAT     | float32, float64 |
| BOOLEAN   | bool |

## Special Considerations

### Generated Columns

Some columns are generated during ETL processing and may not appear in the source schema:

- `AIRCRAFTID`: Generated identifier for aircraft records
- `HISTORIESID`: Generated identifier for history records
- `GENTECHID`: Generated identifier for technical data

These columns are allowed in validation even if not in the schema definition.

### Date/Time Handling

For test fixtures, DATETIME columns may be stored as strings (ISO format) instead of native timestamp types. This is acceptable for test data generation and simplifies fixture creation.

### Nullable Types

Columns that are nullable in the schema may have PyArrow type `null` if they contain no data in the test fixtures. This is valid and represents empty optional columns.

### Views and Derived Tables

Views (e.g., `v_currenthistories`, `v_histories`) may have different column sets than their source tables. Known view tables are skipped in certain validations.

## Implementation Details

### Key Functions

**`get_table_schema(schema_definition, table_name)`**
- Extracts table definition from loaded YAML schema
- Returns column definitions and metadata

**`map_yaml_type_to_pyarrow(yaml_type)`**
- Maps schema type strings to compatible PyArrow types
- Returns list of acceptable PyArrow type objects

**`is_type_compatible(parquet_type, yaml_type)`**
- Validates PyArrow type against schema type
- Handles special cases (nulls, string dates, decimal variants)

### Fixtures

**`schema_definition`** (module scope)
- Loads and caches the YAML schema definition
- Available to all tests

**`input_parquet_files`** (module scope)
- Lists all Parquet files in inputs directory
- Sorted for deterministic test order

**`expected_parquet_files`** (module scope)
- Lists all Parquet files in expected directory
- Sorted for deterministic test order

## Maintenance

### Adding New Tables

When adding new tables to the ETL demo:

1. Add table definition to `ascend_schema.yaml`
2. Generate input and expected Parquet files
3. Run validation tests to ensure compliance

### Updating Schema

When modifying the schema:

1. Update `ascend_schema.yaml` with new columns/types
2. Regenerate affected Parquet files
3. Run tests to validate changes

### Adding Generated Columns

If new generated columns are added:

1. Update `generated_columns` set in test functions:
   ```python
   generated_columns = {"AIRCRAFTID", "HISTORIESID", "GENTECHID", "NEW_COLUMN"}
   ```

## Troubleshooting

### Common Test Failures

**Unknown columns not in schema**
- Check if column is a known generated column
- Verify column exists in schema YAML
- Add to `generated_columns` set if intentionally generated

**Type mismatch errors**
- Verify type mapping is correct
- Check if type needs special handling (dates, decimals)
- Update `is_type_compatible()` if needed

**Missing columns**
- These tests validate that Parquet columns exist in schema
- Parquet files may have subset of schema columns (this is valid)
- Error indicates Parquet has column not defined in schema

**Null values in non-nullable columns**
- Check data generation logic
- Verify schema nullable flags are correct
- Ensure required columns are populated
